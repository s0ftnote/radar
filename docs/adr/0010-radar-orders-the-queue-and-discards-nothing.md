# Radar 只排序不丢弃，排队策略由 Agent 制定

Radar 用机械规则给待判断队列排序，但不用任何规则把内容排除出队列。排序依据是一份**排队策略**：一组带权重的机械信号（新鲜度、端点权重、平台自带热度、关键词命中、该端点在本 Brief 的历史命中率），由用户 Agent 读懂 Brief 之后写出来、下发给 Radar，Radar 逐条算分排序并记账哪些端点与信号真的命中了；Agent 取队列头部若干条判断，再依据这份统计修订策略。Agent 没下发过策略时，Radar 用内置的默认策略（纯新鲜度）。

**排序是两步，不是一条公式**（2026-08-25 修订）。原文把「端点保底配额」写进策略的信号列表，这是个错误：新鲜度、热度、关键词命中都能逐条算分，而配额是**跨端点的合并约束**——它约束的是「结果里每个端点至少占几条」，不是任何单条内容的分值，硬塞进打分公式要么保证不了配额，要么逼出一份说不清的动态状态。因此排序拆成：**先按策略给每条算分，再做一层确定性的端点保底配额**，配额规则由 Radar 固定实现、对所有 Brief 一致，不进策略。配额决定的是**谁进这一包**——每个有候选的端点先保底占一条，剩下的名额纯按分数发；进来之后整包照样按分数排。写成「按第几轮排」就把配额做成了均分：冷门端点的最低分内容会永远排在热门端点的最高分内容前面，分数退化成同轮内的 tie-breaker（2026-08-26 修订）。策略只表达「这条内容值多少分」。

ADR 0009 禁的是 Radar 调模型，不是 Radar 用规则——它给 Radar 的定位本就是"行为完全可预测的采集与排队组件"。真正要守的界线有两条。**第一条是丢弃与排序的区别**：Radar 一旦按规则丢内容，用户就会把"Radar 没给我这个"读成"世界上没发生这件事"，这是最伤信任的一种错误；Demand Radar 这类场景尤其如此——一条有价值的抱怨帖里可能一个关键词都不含。排序则不丢东西，没判到的还在队列里，用户随时可以往下多判。**第二条是先看哪条与什么算相关的区别**：策略只动队列顺序，判断标准仍然只有 Radar Brief，而 Brief 只有用户明确修正才能改变。

替代方案是 Radar 内置一套写死的排序算法，Agent 只当消费者。否掉的理由是两边的强项都没用上：Radar 的强项是持续在线、握有全量历史、会数数、重复执行零成本；Agent 的强项是读懂内容与理解意图。让 Agent 制定、Radar 执行并记账，排序准度随运行时间自我改进，而不取决于设计时拍下的一个公式。

## Consequences

- 排队策略是独立的领域对象，一个 Radar Brief 一份，独立版本化——不能塞进 Radar Brief，否则就破坏了"Brief 只有用户明确修正才能改变"。
- Agent 自行修订策略不构成隐式偏好漂移：策略是显式写下、Radar 存着、可查可改可回滚的对象，且它改变的是顺序不是判断标准。
- Radar 可以执行 Agent 下发的关键词权重，但只能用于加减分，不能用于排除；关键词的提取是 AI 工作，发生在 Agent 侧。
- 不带主题意图的入队规则（去重、时间窗、语言、太短、同一端点单次限量）仍由 Radar 自己决定，它们在任何 Brief 下行为一致，不属于本决定约束的"丢弃"。
- 队列不丢弃意味着它会无限增长：超过保留窗口仍未判断的内容移出待判断队列但不删除，可被显式回捞。这是纯时间规则，不涉及内容。
- Radar 必须为每个端点与每条信号保留命中统计，否则策略修订没有依据；这些统计是纯计数，不读内容。
