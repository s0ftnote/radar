# Web 上只有一张来源页，其余全在 Agent 对话里

> 已由 [ADR 0019](0019-web-is-the-live-workbench-and-agent-is-the-executor.md) 替代：Web 成为任务、内容、报告与来源的实时工作台。下面关于来源页本身怎么排、怎么显示的结论仍然有效。

Radar 的 Web 界面收缩到一个页面：一张采集端点清单，带三态、实例级停用开关、粘网址加源，以及唯一的一处实例级设置（RSSHub 地址）。它就是首页。清单按采集渠道的配置状态排序而**不分区块**——分区块会把「够不着」读成另一类东西，可它跟别的端点一样是这台 Radar 覆盖范围的一部分（#72）。Brief 列表、Brief 正文只读摘要、队列深度与最近判断时间，全部不做——Agent 对话是主入口（ADR 0009），管家角色随时能复述 Brief，队列深度是给取数角色决定「要不要在交付里提一句」用的机械事实，不是给用户看的仪表盘。

**这一页分成两半：在采的，和目录里还能加的**（2026-08-26 修订，#104）。上面那句「不分区块」说的是别按采集渠道的配置状态切块——把「够不着」切出去会让人把它读成另一类东西，这条没变，两半各自内部照旧按配置状态排，不再往下切。新切的这一刀在另一处：出厂目录是目录不是订阅（ADR 0018），登记着不等于在采，把两者混在一张清单里就答不出「这台 Radar 现在到底在采什么」——而那正是这一页存在的理由。下半按 topics 折起来，几十条摊开就是一堵墙；每条带一个要选 Brief 的纳入动作，页面因此有了第二个写动作。「看归网页、改归对话」的界线没破：它写的是纳入这个决定本身，判断标准照旧只在对话里改。

留下来源页而不是一并删掉，理由不是「用户要在这里改东西」——开关和加源在 `radar` CLI 里也做得了，管家角色本来就管这两件事。理由是**看**：几十行渠道端点清单、哪个渠道够不着、哪个端点最近在失败，在对话里逐条念出来很糟，一眼扫完的页面赢。改的入口保留在页面上只是因为它就在眼前，不是因为对话做不到——两个入口写的是同一份 Radar 状态，没有同步问题。相应地，**只有看得清才值得上页面**：Brief 级纳入不上页面（页面是实例级的），加源失败的诊断也不上页面（页面只说一句结果，细节问 Agent）。

这推翻了两条旧结论，都是因为它们的前提没了。#6 要的「Radar 是怎么理解我的」只读摘要，前提是 Web 上有报告页可以挂链接；#8 定的「开关是唯一入口，自然语言拉黑来源不做」，前提是当时没有 CLI，而 #43 已经把端点开关写进了管家角色。#8 怕的「一件事两个入口就要两边同步」在这里不成立。

## Consequences

- 首期试用（#6 的「一句话 → 我先跑一遍 → 在条目上说要不要 → 订」）没有任何 Web 落点，全程在 Agent 对话里，Radar 侧不为它立任何东西——不记「这个 Brief 跑过第一次没有」，第 1 期与第 20 期在 Radar 眼里完全一样。
- 用户找到来源页靠三处：`radar` 安装完成时打印一次 URL、`radar --help`、管家角色在被问起时给链接。不自动开浏览器、不做托盘、不发通知。
- Brief 级纳入只在对话里可见。这是自觉付出的代价：把它搬上页面就要引入 Brief 选择器，页面立刻从一张清单变成一个控制台。
- skeleton 里现存的 Brief 列表页与 Brief 详情页出范围，待删。
