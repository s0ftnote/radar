# 出厂来源目录随版本走，并在升级时与实例对账

出厂来源目录是 Radar 仓库里的一个数据文件，跟代码一起发布，**不做任何在线拉取**。它不是一次性的装机种子：每条端点带一个永不复用的稳定 id，Radar 服务启动时若发现版本号变了，就拿新目录与实例里标记为出厂的端点对账一次——新增的自动加入并默认开，退役的自动实例级停用并显示退役理由，端点搬家（feed 换域名、仓库转移）因为认 id 不认 URL 而只是改个地址。用户自己加的端点一律不碰。

**不在线拉取**，是因为目录改动往往伴随代码改动：加一个新渠道要有新适配器，某个端点的抓取要绕坑。数据与代码脱钩会造出「目录里有这个源，但这一版 Radar 不认这个渠道」这种没人想调的状态；跟着版本走，它在结构上不可能。附带的好处是零运营（在线拉取要求 Radar 有一个上游服务，顶撞 ADR 0008 的开源本地跑）、目录改动走 commit 因而可审计可回滚、离线可用。

**不做一次性种子**，是因为那会让「出厂自带尽量多的来源、你不点开也能用」这条承诺在装机那天冻住——此后 Radar 加的每一个骨干源，老用户永远拿不到，除非重装。而这条承诺恰恰要求老用户也持续受益。代价是 Radar 会在升级时动用户的来源配置，这需要一条清楚的界线，见下。

**Radar 自己观察到的事实永远只导致退避，人写下的决定才导致停用。** 连续采集失败是 Radar 从运行时推断出来的，只退避、永不自动下架（ADR 0010 的同一条界线，#44 已定）；目录退役是维护者的显式决定随版本送达，跟用户在来源页上按停用键是同一类动作，只是执行者不同。许可类退役下继续采就是继续违规，所以这一档必须默认停。两种情况都不删数据。

## Consequences

- 稳定 id 是这个决定唯一严格的地方：一旦发出去就永不复用、永不改写。写错一个 id，用户攒下的来源内容、命中统计与 Brief 级排除就会跟一个不存在的端点绑在一起。
- 目录条目永不从文件里删，只从 `active` 变 `retired` 并带一句理由——删行的话 diff 只能看出「消失了」，来源页上就只见一个源莫名其妙停了。
- 对账静默进行，不弹窗、不汇报、不做迁移向导。用户去来源页才发现多了几行。一个后台采集系统每次升级都汇报来源变动，正是 #8 判定的「训练用户忽略告警」。
- 新增端点默认开不构成负担：ADR 0010 已定队列只排序不丢弃，Agent 永远只取头部若干条，队列变长不改变任何一次判断的成本。
- RSSHub 规则快照是唯一不随版本走的东西，它每天从用户自己那台 RSSHub 实例刷新。它能这样是因为规则只在粘网址那一刻用一次，之后端点与规则库彻底脱钩，更新影响不到任何已有端点——与目录对账（会动真实端点）是两类风险，所以分两套机制。
- 目录改动走普通 PR，收录门槛写在 `AGENTS.md` 里。不做投稿、审核、社区收录，也不做目录的分类体系、评分或推荐——那是把一个数据文件养成一个产品。
