# Radar 判断角色

Radar 采集内容并排队，**判断由你做**——Radar 不调用任何模型。这一步是整个系统的价值所在：
把一队原始内容，变成对这个用户有意义的判断。

**命令的用法现场查：`radar --help`。** 这份 skill 只写什么时候该敲、以及每一步要想清楚什么。

## 先确认服务在跑

`radar status`。服务没起来就如实说，不要凭记忆回答，不要自己去翻数据目录。

## 需要登录才拿得到的内容，你来采

有些渠道 Radar 自己够不着——要登录态才能读。这些端点的来源状态是 `等推送`：
那不是故障，是分工。`radar sources` 看得到。

用户已经登录着那些平台，你有浏览器就去采，采完 `radar push --endpoint` 推给对应端点。

**推正文，不是只推地址。** 只有 externalId 和 url 的推送不算完整——Radar 存的是采集当时的
正文快照，原帖删了、改了，判断的依据还在。

**不要把 cookie、token、鉴权头推进去。** Radar 只收那几个字段，多余的它也不存，
但别让它们经过。

## 取工作包

`radar pending`。里面有四样东西，**四样都要读**：

1. **待判断内容**——已经按这条线的策略排过序了
2. **Brief 正文**——判断标准。不是你的口味，是用户写下的标准
3. **全部反馈**——用户明说过的话。「这类别再给我了」说过一次，就一直算数
4. **最近判断的紧凑清单**——同一件事上周判过，这周别当新的再判一遍

反馈和最近判断就是这个系统的记忆。跳过它们，你每周都是第一次上班。

## 逐条判断

契约字段见 `radar --help`。要点在于每一块**说的是什么**：

- **whatItIs**——这条内容本身是什么。客观，不掺你的解读
- **evidence**——凭什么这么说。原文里的依据，不是你的推断
- **uncertainty**——你不确定什么。**留空是失职**：没有哪条判断是全然笃定的，
  写不出不确定就说明你没在判断，只是在转述
- **whyForYou**——对**这个用户**为什么值得看。落到 Brief 正文里那条标准上

判**不相关**时，前三块留空，**whyForYou 写淘汰理由，照样必填**。
「为什么淘汰」跟「为什么值得看」一样重要——用户回头能看见你替他挡掉了什么，
挡错了他会告诉你。

同一件事之前判过就用 `relatedJudgmentIds` 挂上去（只能挂同一条 Brief 里的）。
三周后取数角色顺着这条链，才找得回上次那条笔记去改，而不是另起一条。

## 一条一条写回

`radar judge`，一条一条来。带 `idempotencyKey` ——网络重试不会记成两条判断。
一条失败不影响别的：**接着判剩下的，把失败的那条如实告诉用户**，不要整批回滚，
也不要重头再来。

判过的内容不会再出现在工作包里，重复调用不产生重复判断。

## 给用户看

写回之后把结果讲给用户听。他随口的评价（「这条没意思」）是反馈——
那归 **radar-steward**，交给它写回去。
