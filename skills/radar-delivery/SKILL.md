# Radar 取数角色

Radar 存着判断，**输出由你写**。你取素材，写完把报告正文保存回 Radar，再把
「送到哪儿了」记回去。WebUI 与 Agent 读的是同一份报告。

**命令用法现场查 `radar --help`。** 这份 skill 写的是时机与记账的规矩。

## 开工前

`radar status`。服务没起来就照实说，让用户先 `radar up`；素材一律现取，不用记忆里的旧判断
凑一份周报。

接着 `radar queue`。用户要的是「最近」，而队列里还堆着没判的——先接上 **radar-judgment**
判一包再取，不然给他的是上周判到哪儿算哪儿。队列空或用户只要已判过的，直接取。

## 去处是用户自己起的标签

`周报`、`obsidian`、`月度复盘`——Radar 不预设可选值也不校验。**同一个去处每次用同一个
字符串**，这是这本账唯一的对齐方式。今天写 `周报`、下周写 `weekly`，那就是两本账。

## 取素材

`radar deliver take` 默认给**这个去处还没送过的**判断，也就是增量。另外三种取法：

- **时间窗**——「上个月都有什么」
- **关注对象**——「某某最近怎么样」，按名字与别名机械匹配
- **关联链**——「这件事上次是怎么写的」。链上带着出发那条自己，也带着**已经送过的**，
  正是为了找回上次那条；配 `radar deliver history` 拿到它的外部引用

淘汰掉的判断不进素材——它的正文只有一条淘汰理由。

## 出报告之前看一眼两个机械事实

`radar queue` 给队列深度与最近一次判断时间，`radar sources` 给来源状态。都是 Radar 数得
出来的事实，不含判断。提不提由你定：

- 队列很深、最近一次判断还停在上上周 → 这一期是从一小半内容里挑出来的，**提一行**，
  别让用户以为覆盖是全的
- 某个来源整段窗口都「最近失败」→ 那一块是缺的，同样提一行
- 一切正常 → 一个字都不用说。每期都念一遍状态等于没说

判据是「只在可能影响本期结论时提示一行」。

## 写输出

素材是判断，不是原文摘要。whatItIs / evidence / uncertainty / whyForYou 四块都用上，
**uncertainty 照样写进输出**——用户才知道哪些还需要自己看一眼。

报告写完先用 `radar report create` 保存回这条 Brief，并带上实际使用的判断 id。
标题、正文、生成者与取材关系都要完整；网络重试使用同一个幂等键，不能让 WebUI
出现两份相同报告。

**往知识库里写，用用户那边已有的 skill**——Obsidian、Notion、llm-wiki 之类各有自己的写法与存储
约定，这份 skill 不替它们定。顺序是：先从 Radar 取素材，写报告并保存回 Radar，再按那边的 skill
写进去，写完把它给你的定位（笔记路径、note id、页面链接）当外部引用记回 Radar。用户没装那类 skill、又要往笔记库写，
问他笔记库在哪、怎么写，别自己发明一套目录结构。

## 送完记账

`radar deliver mark`，一条一条记。

- **送到了才记。** 取了没送就先别记，记了那条从此消失在增量里
- **写进笔记库了就带上外部引用**：Obsidian 路径、note id、文档链接都行。Radar 不解释它，
  只保证它还在。三周后同一件事又冒出来，你靠它找回那条笔记去改
- 同一条判断送去多个去处，各记各的，互不影响
- 重复标记是**幂等**的：同一对（判断，去处）不会记成两笔

跨系统没法原子提交，规矩是**至少一次交付**：先送，再记账。中间断了就重记一次。

**做完的标准：报告已经保存回 Radar；这一期送出去的每一条都记了账。**

## 账实不符

用户说「这条你上周明明没给我」，或者笔记建到一半失败了——`radar deliver unmark`，那条回到
增量里，下次重新给你。那是记错账，Brief 与判断都不必动。

用户读完随口的评价（「这条没意思」）是反馈，归 **radar-steward**。
